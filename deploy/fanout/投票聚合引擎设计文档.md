# 投票聚合引擎设计文档

> N 个 Agent 并发处理同一任务，收集结果后按字段级投票聚合，输出最终结果。独立于 OpenFang，作为投票网关的核心模块。
>
> **核心设计原则：引擎不感知字段名。** 提取哪些字段是不固定的（合同、发票、报关单字段各不同），引擎只关心值的类型，按类型自动选择规范化器和比较策略。

---

## 0-1. 场景分析：标注 Manifest 的投票适配

### 当前场景

用户的 Manifest 不是扁平的 `{"field": "value"}` 结构，而是**基于坐标的标注文件**：

- Manifest 解析发票/合同图片
- 每个标注项通过 **bbox 坐标** 关联到图片上的区域
- 包含 label（标签类型）、bbox（坐标）、content（提取内容）等结构化信息
- 不同 Agent 处理同一张图片时，可能：
  - 检测到不同数量的标注项
  - 给同一区域赋予不同的 label（如 `"amount"` vs `"total"`）
  - 给同一区域划定略有差异的 bbox 坐标
  - 提取的 content 格式不同（如 `"150,000.00元"` vs `"150000.00"`）

### 与扁平 JSON 投票的核心区别

| 维度 | 扁平 JSON 投票（已设计） | 标注 Manifest 投票（需扩展） |
|------|------------------------|--------------------------|
| 数据结构 | `{"key": "value"}` | `[{"label": ..., "bbox": [...], "content": ...}]` |
| 对齐方式 | 按 key 直接匹配 | 需要**先对齐再投票** |
| 主要复杂度 | 值的规范化 | 项的匹配（哪个 Agent 的第 i 项对应哪个 Agent 的第 j 项） |
| 坐标投票 | 无 | bbox 坐标也需要投票（取中位数或均值） |

### 投票两步法：先对齐，再投票

```
Step 1: 对齐（Alignment）
  Agent 1: [A1, A2, A3]    ─┐
  Agent 2: [B1, B2, B3]    ─┤ 找到哪些项是"同一个东西"
  Agent 3: [C1, C2, C3]    ─┘

  对齐结果: (A1,B1,C1), (A2,B2,C2), (A3,B3,C3)
            可能出现: (A3,B2,?) → Agent 3 没有匹配项

Step 2: 投票（Vote per group）
  对每个对齐组:
    - label 投票: "amount" × 7, "total" × 3 → "amount"
    - bbox 投票: 坐标取均值/中位数
    - content 投票: 与扁平 JSON 相同，按类型规范化后多数表决
```

### 对齐策略（配置化，适配不同场景）

| 策略 | 匹配依据 | 适用场景 | 配置 |
|------|----------|----------|------|
| `label_match` | label 完全相同 | 标注体系统一、label 确定性强 | `align_strategy: "label"` |
| `bbox_iou` | bbox 交并比 > 阈值 | label 不稳定但位置稳定 | `align_strategy: "bbox", iou_threshold: 0.5` |
| `label_or_bbox` | label 相同 OR bbox IoU > 阈值 | 混合策略（推荐） | `align_strategy: "label_or_bbox", iou_threshold: 0.3` |
| `content_similarity` | 提取内容相似度 | 无 label 无固定位置 | `align_strategy: "content", similarity_threshold: 0.8` |

### 对齐算法核心：匈牙利匹配

当 N 个 Agent 各返回 M 个标注项时，对齐是**二分图匹配问题**，用匈牙利算法求解：

```
输入: 两个 Agent 的标注列表 list_a, list_b
匹配代价矩阵: cost[i][j] = 1 - similarity(list_a[i], list_b[j])
  similarity 可以是:
    - label_match:  label_a == label_b ? 1.0 : 0.0
    - bbox_iou:     IoU(bbox_a, bbox_b)
    - hybrid:       0.5 * label_match + 0.5 * bbox_iou

输出: 最佳匹配对 [(i1,j1), (i2,j2), ...]
未匹配的项标记为 ORPHAN
```

### 投票引擎的两层架构

```
┌─────────────────────────────────────────┐
│  Layer 1: 项级对齐 + 投票               │
│  (annotation_vote)                       │
│                                          │
│  输入: N 个 Manifest（每个含 M 个标注项）│
│                                          │
│  1. 两两匈牙利对齐                       │
│  2. 对齐组合并为"对齐组"                 │
│  3. 每个对齐组内：                       │
│     - label 投票（多数表决）             │
│     - bbox 投票（坐标取中位数）          │
│     - content 投票 → 调用 Layer 2        │
│                                          │
│  输出: 合并后的 Manifest                 │
└──────────────┬──────────────────────────┘
               │ content 投票委托
               ▼
┌─────────────────────────────────────────┐
│  Layer 2: 值级投票（已设计的部分）       │
│  (field_majority)                        │
│                                          │
│  类型推断 → 规范化 → 分组 → 计票       │
│  支持: string / number / date / ...      │
│  这层不关心值来自哪个标注项             │
└─────────────────────────────────────────┘
```

### 抽象程度：三种场景的适配

**场景 A：扁平 JSON 提取（如 `{"amount": "150000"}`）**
- 只用 Layer 2
- 不需要对齐，直接按 key 匹配

**场景 B：标注 Manifest（如发票 bbox 标注）**
- Layer 1 对齐 + Layer 2 content 投票
- bbox 坐标在 Layer 1 内投票

**场景 C：自由文本（如合同风险摘要）**
- 只用 `llm_arbitrate` 策略
- 不需要对齐，LLM 聚合

引擎通过 `vote_config` 的 `data_mode` 字段选择走哪条路径：

```json
{
  "vote_config": {
    "data_mode": "annotation",  // "flat" | "annotation" | "text"
    "strategy": "field_majority",
    "align_strategy": "label_or_bbox",
    "iou_threshold": 0.3,
    "quorum": 0.5,
    "tie_break": "llm",
    "min_success": 3
  }
}
```

### 待确认

- [ ] 真实 Manifest 的字段结构（待用户提供示例文件）
- [ ] bbox 格式（`[x1,y1,x2,y2]` vs `{"x":..., "y":..., "w":..., "h":...}`）
- [ ] 是否有 label 层级（如 `"amount"` 下分 `"subtotal"` / `"tax"` / `"total"`）
- [ ] content 是纯文本还是可能包含子结构

## 0. 类型自动推断（核心机制）

引擎在运行时动态发现所有字段，对每个字段的值自动推断类型，选择对应的规范化器。

### 0.1 类型推断规则

按优先级从高到低判断，命中即停止：

```python
def infer_type(value) -> str:
    """
    返回: "null" | "number" | "date" | "boolean" | "array" | "object" | "string"
    """
    if value is None:
        return "null"

    # 数组
    if isinstance(value, list):
        return "array"

    # 对象（嵌套 dict）
    if isinstance(value, dict):
        return "object"

    # 布尔
    if isinstance(value, bool):
        return "boolean"

    # 数字（含字符串形式的数字）
    s = str(value).strip()
    if is_number_like(s):
        return "number"

    # 日期
    if is_date_like(s):
        return "date"

    # 默认字符串
    return "string"
```

### 0.2 is_number_like 判断逻辑

```python
import re

def is_number_like(s: str) -> bool:
    """判断字符串是否像数字"""
    # 去掉常见前后缀后判断
    cleaned = s
    # 去货币符号
    cleaned = re.sub(r'^[￥¥$€£]', '', cleaned)
    # 去千分位逗号
    cleaned = cleaned.replace(',', '')
    # 去中文单位
    cleaned = re.sub(r'[元万百千万亿角分整]+$', '', cleaned)
    cleaned = cleaned.strip()

    # 尝试转 float
    try:
        float(cleaned)
        return True
    except ValueError:
        # 中文数字（壹拾伍万元整）
        return bool(re.match(r'^[零壹贰叁肆伍陆柒捌玖拾佰仟万亿圆角分整]+$', cleaned))
```

### 0.3 is_date_like 判断逻辑

```python
def is_date_like(s: str) -> bool:
    """判断字符串是否像日期"""
    patterns = [
        r'^\d{4}[-/]\d{1,2}[-/]\d{1,2}$',       # 2026-03-15, 2026/03/15
        r'^\d{4}年\d{1,2}月\d{1,2}日?$',          # 2026年3月15日
        r'^\d{8}$',                                 # 20260315
        r'^\d{4}[-/]\d{1,2}$',                     # 2026-03（年月）
        r'^[A-Z][a-z]{2}\s+\d{1,2},?\s+\d{4}$',  # Mar 15, 2026
    ]
    return any(re.match(p, s.strip()) for p in patterns)
```

### 0.4 类型 → 规范化器映射

```python
TYPE_NORMALIZER = {
    "null":    lambda v: None,
    "number":  number_normalize,
    "date":    date_normalize,
    "boolean": lambda v: str(v).lower(),       # True/true → "true"
    "array":   json_normalize,                 # 序列化后排序比较
    "object":  json_normalize,                 # 递归：内部每个字段再做类型推断
    "string":  strip_normalize,                # 默认 trim
}
```

**注意：** 引擎启动时不需要配置任何字段名。所有字段、所有类型都在运行时从 Agent 输出中动态推断。

## 1. 输入输出契约

### 1.1 输入

```json
{
  "task_id": "uuid-string",
  "results": [
    {
      "agent_id": "processor-1",
      "status": "success",
      "output": "{ \"contract_name\": \"XX采购合同\", \"total_amount\": \"150000.00\", \"sign_date\": \"2026-03-15\", \"party_a\": \"XX有限公司\", \"party_b\": \"YY科技有限公司\", \"items\": [ { \"name\": \"设备A\", \"quantity\": \"10\", \"unit_price\": \"5000.00\" } ] }"
    },
    {
      "agent_id": "processor-2",
      "status": "success",
      "output": "{ \"contract_name\": \"XX采购合同\", \"total_amount\": \"150,000.00元\", \"sign_date\": \"2026年3月15日\", \"party_a\": \"XX有限公司\", \"party_b\": \"YY科技有限公司\", \"items\": [ { \"name\": \"设备A\", \"quantity\": \"10\", \"unit_price\": \"5000.00\" } ] }"
    },
    {
      "agent_id": "processor-3",
      "status": "failed",
      "output": null
    }
  ],
  "vote_config": {
    "strategy": "field_majority",
    "quorum": 0.5,
    "tie_break": "llm",
    "min_success": 3
  }
}
```

**字段说明：**

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `results[].output` | string | 成功时必填 | Agent 的原始输出，必须是合法 JSON 字符串 |
| `results[].status` | string | 是 | `success` 或 `failed`，failed 的条目直接排除 |
| `vote_config.strategy` | string | 是 | 聚合策略，见第 3 节 |
| `vote_config.quorum` | float | 否 | 默认 0.5，最低得票比例 |
| `vote_config.tie_break` | string | 否 | 平局处理：`first`（取第一个）| `llm`（LLM 仲裁）| `null`（标记 UNRESOLVED）|
| `vote_config.min_success` | int | 否 | 默认 3，成功 Agent 数低于此值则整个投票失败 |
| `vote_config.type_overrides` | object | 否 | 手动覆盖特定字段的类型推断，见下文 |

**type_overrides 说明：** 引擎默认自动推断值的类型，但某些字段可能需要手动覆盖。例如某个字段值是 `"2026-03"` 但你不希望它被当作日期处理：

```json
{
  "vote_config": {
    "strategy": "field_majority",
    "quorum": 0.5,
    "tie_break": "llm",
    "min_success": 3,
    "type_overrides": {
      "version": "string",
      "contract_no": "string"
    }
  }
}
```

不配置 `type_overrides` 时，引擎完全自动推断，不需要知道任何字段名。

## 2. 规范化器实现

投票前，每个值根据自动推断的类型选择规范化器，使等价值能被正确识别。引擎不按字段名配置，完全按值类型驱动。

### 2.1 各类型规范化规则

| 值类型 | 规范化器 | 输入示例 | 输出 |
|--------|----------|----------|------|
| `string` | strip（去前后空格） | `"  XX有限公司 "` | `"XX有限公司"` |
| `number` | number_normalize | `"150,000.00元"` `"￥150000.00"` `"壹拾伍万元整"` | `"150000.00"` |
| `date` | date_normalize | `"2026年3月15日"` `"2026/03/15"` `"Mar 15, 2026"` | `"2026-03-15"` |
| `boolean` | lower | `True` `False` | `"true"` `"false"` |
| `array` | json_normalize | `[{"b":1},{"a":2}]` | 排序后的 canonical JSON 字符串 |
| `object` | json_normalize（递归） | `{"b":1,"a":2}` | `{"a":2,"b":1}` |
| `null` | — | `null` / `None` | 保持 `null` |

### 2.2 number_normalize 实现要求

```
输入: 可能包含以下格式的字符串
  - "150,000.00"       → 去千分位逗号
  - "150000.00元"      → 去中文后缀
  - "￥150,000.00"     → 去货币符号
  - "壹拾伍万元整"      → 中文数字转阿拉伯数字（如果无法转换，返回原值）
  - "150000"           → 保持
  - "150000.0"         → 保持
  - "-500.00"          → 保持负号

输出: 字符串，统一为不带逗号、不带单位的小数形式
  - 如果输入不是合法数字（如 "不详"、"待定"），返回原值不做转换
```

### 2.3 date_normalize 实现要求

```
支持格式:
  - "2026-03-15"         → "2026-03-15"
  - "2026/03/15"         → "2026-03-15"
  - "2026年3月15日"       → "2026-03-15"
  - "20260315"           → "2026-03-15"
  - "Mar 15, 2026"       → "2026-03-15"
  无法解析的返回原值
```

### 2.4 json_normalize 实现要求

```
输入: Python dict 或 list
处理:
  1. 递归遍历所有嵌套 dict/list
  2. dict 按 key 字母序排序
  3. 序列化为 JSON 字符串（ensure_ascii=False, separators=(',', ':'), sort_keys=True）
  4. 如果数组内元素是 dict，每个 dict 也按 key 排序后再比较
输出: canonical JSON 字符串，用于精确比较
```

### 2.5 object 类型的递归处理

当某个字段值是嵌套对象时，**不要对整个对象做字符串比较**，而是递归到对象内部，对每个子字段独立做类型推断 → 规范化 → 投票。

```
例如 Manifest 中有嵌套结构:
{
  "items": [
    {"name": "设备A", "quantity": "10", "unit_price": "5000.00"},
    {"name": "设备B", "quantity": "5",  "unit_price": "8000.00"}
  ]
}

处理方式:
  1. "items" 被推断为 array 类型
  2. 数组比较策略：按元素位置逐个比较
  3. 每个元素是 object → 递归：对 "name" 用 string 比较，对 "quantity" 和 "unit_price" 用 number 比较
  4. 如果不同 Agent 返回的数组长度不同：
     - 取最常见长度（多数投票）
     - 多出的元素标记为 UNRESOLVED
```

### 2.6 不同长度数组的处理

这是最常见的边界情况。10 个 Agent 中可能有 8 个返回 3 个 item、2 个返回 2 个 item。

```
处理策略:
  1. 统计数组长度，取众数（多数 Agent 返回的长度）
  2. 只对众数长度内的索引做逐元素投票
  3. 多出/缺少的元素：
     - 如果某些 Agent 多出元素且内容一致 → 保留
     - 如果不一致 → 标记为 UNRESOLVED
```

## 3. 三种聚合策略

### 3.1 field_majority（推荐，用于结构化 JSON）

**算法伪代码：**

```
function field_majority_vote(results, config):
    # 1. 过滤掉 failed 的结果
    valid = [r for r in results if r.status == "success"]
    if len(valid) < config.min_success:
        return VoteFailed("success count below min_success")

    # 2. 解析 JSON
    manifests = []
    for r in valid:
        try:
            manifests.append(json.loads(r.output))
        except JSONDecodeError:
            log.warning(f"Agent {r.agent_id} output is not valid JSON, skipping")
    if len(manifests) < config.min_success:
        return VoteFailed("parseable count below min_success")

    # 3. 动态发现所有字段（不预设字段名）
    all_fields = union of all keys across manifests

    # 4. 对每个字段独立投票
    final = {}
    field_details = {}

    for field in all_fields:
        values = [m[field] for m in manifests if field in m]
        if not values:
            continue

        # 4a. 自动推断类型（不按字段名，按值的内容推断）
        #     如果有 type_overrides 配置，优先使用
        if field in config.type_overrides:
            value_type = config.type_overrides[field]
        else:
            # 取第一个非 null 值推断类型
            value_type = infer_type(first_non_null(values))

        # 4b. 根据 type 选择规范化器
        normalizer = TYPE_NORMALIZER[value_type]

        # 4c. 特殊处理：object 和 array 递归投票
        if value_type == "object":
            # 递归：对嵌套对象的每个子字段做独立投票
            nested_results = vote_nested_object(values, config)
            final[field] = nested_results["final_result"]
            field_details[field] = nested_results["vote_detail"]
            continue

        if value_type == "array":
            # 递归：对数组按索引逐元素投票
            array_result = vote_array(values, config)
            final[field] = array_result["final_result"]
            field_details[field] = array_result["vote_detail"]
            continue

        # 4d. 标量字段：规范化 → 分组 → 计票
        normalized = [(v, normalizer(v)) for v in values]
        groups = group_by(normalized, key=lambda x: x[1])

        # 4e. 排序，最多的组在前
        sorted_groups = sort(groups, key=lambda g: len(g), reverse=True)
        winner_group = sorted_groups[0]
        confidence = len(winner_group) / len(values)

        # 4f. 判断是否达到 quorum
        if confidence >= config.quorum:
            final[field] = winner_group[0][0]  # 保留原始值格式
        elif config.tie_break == "llm" and len(sorted_groups) > 1:
            final[field] = llm_tie_break(field, values)
            confidence = -1  # 标记为仲裁结果
        else:
            final[field] = winner_group[0][0]
            confidence = len(winner_group) / len(values)

        field_details[field] = {
            "value": final[field],
            "inferred_type": value_type,
            "votes": f"{len(winner_group)}/{len(values)}",
            "confidence": round(confidence, 2),
            "groups": [
                {
                    "normalized": norm_val,
                    "count": len(group),
                    "raw_values": [item[0] for item in group]
                }
                for norm_val, group in groups.items()
            ]
        }

    # 5. 计算整体置信度
    overall = average of all field confidences

    return {
        "status": "completed",
        "final_result": final,
        "vote_detail": {
            "strategy": "field_majority",
            "total_replicas": len(results),
            "success_replicas": len(valid),
            "fields": field_details,
            "overall_confidence": round(overall, 2)
        }
    }
```

**递归投票辅助函数：**

```
function vote_nested_object(object_values: list[dict], config) -> dict:
    """对嵌套对象的每个子字段递归调用 field_majority_vote"""
    sub_fields = union of keys across object_values
    result = {}
    for key in sub_fields:
        sub_values = [o[key] for o in object_values if key in o]
        sub_type = infer_type(first_non_null(sub_values))
        # 递归处理...
    return {"final_result": result, "vote_detail": details}


function vote_array(array_values: list[list], config) -> dict:
    """对数组按索引逐元素投票"""
    # 1. 先对数组长度投票（取众数）
    lengths = [len(a) for a in array_values]
    majority_length = most_common(lengths)

    # 2. 逐索引投票
    result = []
    for i in range(majority_length):
        element_values = [a[i] for a in array_values if i < len(a)]
        element_type = infer_type(first_non_null(element_values))
        if element_type == "object":
            result.append(vote_nested_object(element_values, config))
        else:
            result.append(vote_scalar(element_values, config))

    return {"final_result": result, "vote_detail": details}
```

**数组字段（items）的特殊处理：**

`items` 是对象数组。比较策略：将数组中的每个元素序列化为 `json_normalize` 后的字符串，整体作为字符串比较。如果数组长度不同，长度也作为一个比较维度。

### 3.2 whole_majority（整体匹配，最简单）

**算法：**

```
function whole_majority_vote(results, config):
    valid = filter success(results)
    manifests = parse_json(valid)

    # 将整个 manifest 序列化为 canonical JSON（sort keys, indent=None）
    canonical = [json.dumps(m, sort_keys=True, ensure_ascii=False) for m in manifests]

    # 分组计数
    groups = Counter(canonical)
    winner, count = groups.most_common(1)[0]
    confidence = count / len(canonical)

    if confidence < config.quorum:
        return tie_break_or_fail(...)

    return {
        "final_result": json.loads(winner),
        "vote_detail": {
            "strategy": "whole_majority",
            "winner_count": count,
            "total": len(canonical),
            "confidence": confidence
        }
    }
```

**适用场景：** Agent 输出非常稳定、格式完全一致的情况。对 Manifest 场景不太推荐，因为即使只有一个字段差一个字，整体就不匹配。

### 3.3 llm_arbitrate（LLM 仲裁，最灵活）

**算法：**

```
function llm_arbitrate(results, config):
    valid = filter success(results)
    manifests = parse_json(valid)

    # 构造仲裁 prompt
    prompt = f"""
你是一个数据质量审核员。以下是 {len(manifests)} 个 Agent 对同一份文件的处理结果。
请仔细对比每个字段，综合判断，输出一份最准确的最终结果。

Agent 结果列表：
{json.dumps(manifests, ensure_ascii=False, indent=2)}

要求：
1. 直接输出最终结果的 JSON，不要解释
2. 对于数值字段，选择出现最多的值
3. 对于文本字段，如果存在差异，选择最完整、最准确的
4. 输出必须是合法 JSON
"""

    response = call_llm(
        model=config.arbiter_model,
        messages=[{"role": "user", "content": prompt}],
        temperature=0.1
    )

    return {
        "final_result": json.loads(response),
        "vote_detail": {
            "strategy": "llm_arbitrate",
            "arbiter_model": config.arbiter_model,
            "total_replicas": len(results),
            "success_replicas": len(valid)
        }
    }
```

**LLM 仲裁的 tie_break 模式（field_majority 平局时调用）：**

```
function llm_tie_break(field_name, values):
    prompt = f"""
在合同处理任务中，字段 "{field_name}" 的 {len(values)} 个 Agent 返回了不同值：
{json.dumps(values, ensure_ascii=False)}
请选择最准确的一个值，只输出该值本身，不要解释。
"""
    return call_llm(prompt, temperature=0.0)
```

## 5. 错误处理

| 场景 | 处理 |
|------|------|
| 成功 Agent 数 < min_success | 返回 `vote_failed`，附 partial_results |
| Agent 输出不是合法 JSON | 跳过该条，log warning，不影响其他 |
| LLM 仲裁调用失败 | 降级为取出现最多的值；都失败则返回 `vote_failed` |
| 所有字段都低于 quorum 且无 tie_break | 返回 `vote_failed` |
| 规范化器解析失败（如无法识别的日期） | 保留原值，按原值参与投票 |

```python
     "output": '{"invoice_no": "FP20260315001", "seller": "XX有限公司", "tax_amount": "13,500.00元", "issue_date": "2026/03/15"}'},

    {"agent_id": "p3", "status": "success",
     "output": '{"invoice_no": "FP20260315001", "seller": "XX有限公司", "tax_amount": "13500.00", "issue_date": "2026-03-15"}'},

result = field_majority_vote(invoice_results, config={
```

### 7.6 嵌套数组投票

```python
results = [
    {"agent_id": "p1", "status": "success",
     "output": '{"items": [{"name": "设备A", "price": "5,000.00"}, {"name": "设备B", "price": "8,000.00"}]}'},
    {"agent_id": "p2", "status": "success",
     "output": '{"items": [{"name": "设备A", "price": "5000.00"}, {"name": "设备B", "price": "8000.00"}]}'},
    {"agent_id": "p3", "status": "success",

]

result = field_majority_vote(results, config={
    "quorum": 0.5, "min_success": 3, "type_overrides": {}
})

# 数组长度投票：[2, 2, 1] → 众数 2
# items[0].name: "设备A" × 3 → 一致
# items[0].price: "5000.00" × 3 (normalize后) → 一致
# items[1] 只有 p1 p2 有 → 2/3 投票
assert len(result["final_result"]["items"]) == 2
```
